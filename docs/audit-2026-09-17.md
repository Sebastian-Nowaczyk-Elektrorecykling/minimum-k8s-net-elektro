# Repository audit — 17 September 2026

Baseline: `687535404d5f9e3a840e5f6149a9f4e782e5d04d`. Scope: all tracked setup,
removal and configuration scripts; Flux dependencies/ownership; Cilium and
cert-manager chart output; Gateway/TLS/DNS manifests; examples; CI and operating
instructions. This is a source/configuration audit with automated validation,
not an inspection of a running cluster or a complete image/package CVE scan.

## Findings addressed

| Impact | Finding | Change |
| --- | --- | --- |
| High | Local-PV removal checks only recognized a hostname `In`-style value equal to the Node name. Custom hostname labels, rack selectors, matchFields and unscoped hostPath PVs could escape the check. | Evaluate node-affinity terms against actual labels/fields; block unscoped hostPath volumes; retain storage and require migration/retirement. |
| High | Removing the server running the maintenance command could stop the local API/etcd before membership verification. | Reject routine self-removal before drain/stop; explicit final-server destruction remains available. |
| High | CA reads redirected directly over backups; API failures could truncate files. A partial local pair could cause a new trust root to be generated. | Read the Secret once, distinguish absence from API errors, stage and verify the pair, preserve backups on failure, and reject partial local pairs. |
| Medium | Gateway readiness relied on generic Flux resource handling; it did not explicitly check each listener, parent or current generation. | Add CEL health checks and a read-only live acceptance script; test stale, empty, failed and wrong-parent status. |
| Medium | Bootstrap waited for only Gateway and HTTPRoute CRDs before starting Cilium. | Wait for the entire pinned CRD bundle, including the other APIs required by Cilium 1.20. |
| Medium | Ingress was absent from authored routes, but chart defaults controlled whether Cilium/Hubble enabled it; cert-manager still enabled ingress-shim. | Explicitly disable legacy routing and ingress-shim; enforce Gateway-only resources and controller settings in rendered output. |
| Medium | CI never enabled optional built-in Kubernetes schema validation; unknown custom schemas could silently pass. | Require kubeconform, use the pinned Kubernetes version, and reject missing/unserved/deprecated custom-resource schemas. Include the deployable application example and Helm output. |
| Medium | Host preparation did not explicitly load VXLAN and the netfilter modules used by Cilium's default L7 proxy path. | Persist and load `vxlan`, `xt_socket`, `xt_TPROXY`, `xt_mark`, and `xt_CT`; unsupported kernels fail during preparation. |
| Medium | Configuration accepted unknown fields, malformed field types, unpinned versions and private DNS zones overlapping `cluster.local`. | Reject those inputs before manifest generation; add regression cases for silent typos and DNS shadowing. |
| Low | CI downloaded Kustomize without verifying its release checksum. | Verify Kustomize and the newly required kubeconform archives against published checksums. |

## Routing and compatibility result

The baseline already used Gateway API. There were no repository-owned Ingress
or IngressClass resources to translate. The change removes remaining reliance
on legacy controller behavior and prevents reintroduction. Read the
[migration guide](gateway-migration.md) for Ingress resources introduced by
other owners and for live acceptance commands.

The existing k3s 1.36 / Cilium 1.20 / Gateway API 1.6.1 pins match the
[Cilium compatibility matrix](https://docs.cilium.io/en/stable/network/kubernetes/compatibility/)
and [Gateway API requirements](https://docs.cilium.io/en/stable/network/servicemesh/gateway-api/gateway-api/).
The audit does not perform an unnecessary dependency upgrade. Kustomize's
`kustomize.config.k8s.io/v1beta1` files are build configuration, not deprecated
Kubernetes Ingress APIs.

Kernel preparation follows Cilium's
[L7 proxy requirements](https://docs.cilium.io/en/stable/operations/system_requirements/#requirements-for-l7-and-fqdn-policies).
Flux readiness uses its documented
[custom health expressions](https://fluxcd.io/flux/components/kustomize/kustomizations/#health-check-expressions).
Cert-manager's [controller selection](https://cert-manager.io/docs/cli/controller/)
disables ingress-shim while retaining explicit Certificate reconciliation.

## Preserved constraints and operating limits

- The only static LAN endpoint remains `192.168.2.153`; DNS, API and Gateway
  availability still depend on that host. Additional etcd members do not remove
  this deliberate single point of failure.
- Hubble stays enabled within Cilium, with direct bootstrap access and a
  configurable SSO proxy backend. No external observability stack is added.
- Longhorn/GPU setup remains host prerequisites only. No storage or GPU
  operator/device plugin is installed.
- The node power policy still ignores lid/idle/desktop sleep and permits the
  physical power button to suspend. Root/firmware behavior and existing desktop
  inhibitor locks retain the documented limitations.
- TLS uses a private CA. Back up its key and the etcd token/snapshots off-host.
  Host-network listeners and metrics still require the documented firewall
  restrictions; this repository is not a hostile multi-tenant security boundary.
- The CI checks render and validate resources and exercise DNS, policy health
  expressions, address selection, CA failure paths and local-volume safeguards.
  Debian installation, real hardware suspend/GPU behavior, Cilium datapath,
  Flux adoption and LAN traffic still require checks on actual nodes.

## Applying the changes

Flux applies the manifest/controller changes from the configured branch.
Host changes require updating the checkout on each node and rerunning host
preparation during maintenance (`sudo ./scripts/prepare-host.sh`); it can also
update packages/drivers. Existing normal Gateway routes keep their names,
addresses, certificates and backend ownership. Complete any external Ingress
migration before relying on the Gateway-only acceptance check. Run
`sudo ./scripts/check-gateway.sh` on a controller, then the LAN DNS/HTTPS tests.
